## Scope

Use this server for human population frequency and gene constraint evidence, or for ClinVar gene-level curation followed by population lookups. Core lookups and ClinVar search are keyless. It does not translate coordinates between builds: an absent coordinate ID whose string also lifts over from the other build fails as `variant_not_found_other_build` with the lifted IDs in `candidates`, a hint the server never acts on. It does not annotate structural or mitochondrial variants or submit clinical classifications.

For a single candidate, the user-invoked `gnomad_variant_triage` prompt already supplies the frequency, constraint, and callability workflow. The workflows below address candidate discovery and cross-source follow-up.

## Identifiers

- Resolve an Ensembl gene ID to its HGNC symbol before `gnomad_search_clinvar`; other gene tools accept the Ensembl ID directly (versioned or lowercase forms included). An Ensembl lookup can supply the symbol.
- ClinVar search returns its own VariationID and accession for provenance. Neither is a gnomAD variant identifier; the HGVS title is not one either.
- Prefer a returned `grch38_variant_id` for `gnomad_get_variant` on a GRCh38 dataset. It is derived from the SPDI for SNVs, MNVs, and delins, and for deletions, insertions, and duplications it is filled from gnomAD's own ClinVar mapping; most of those indel IDs are absent from gnomAD, so `variant_not_found` there is absence evidence to pair with `gnomad_get_coverage`, not a failed conversion. When it is null (mitochondrial, multi-allele, copy-number, or structural records, records newer than gnomAD's ClinVar release, or a mapping notice reporting the gnomAD request failed), the row may still supply dbSNP rsIDs; split the semicolon-joined `rsids` into individual identifiers before lookup.
- A canonical SPDI is not a VCF-style gnomAD ID. SPDI positions are zero-based; canonical insertions and deletions can be repeat-expanded and lack the VCF anchor base. Do not construct a gnomAD ID by replacing separators or merely adding one to the position. Obtain a normalized allele on the required build from a reference-aware source instead.

## Gates

- Before following an rsID into population evidence, inspect its batch outcome. For `ambiguous_rsid`, select the concrete allele matching the candidate from `candidates`, or resolve it through dbSNP or Ensembl when candidates are unavailable. Do not choose the first candidate by position.
- Before reading a `variant_not_found_other_build` item as absence or as a wrong-build ID, decide which build the ID was written for. If it was written for the other build, look up a candidate on the same dataset; if not, it is absent, so check coverage at its position. A resolved lift does not prove a mismatch: a valid ID truly absent from the dataset lifts too.
- Before treating an unknown gene or transcript on `gnomad_list_gene_variants` or `gnomad_get_coverage` as an empty gene, read its `gene_not_found` / `transcript_not_found` failure: gnomAD holds no such ID in this build. Pass Ensembl transcript IDs (`ENST…`), not RefSeq (`NM_…`).
- Before calling a ClinVar search complete, follow `next_offset` until it is null. For `pathogenic`, `likely pathogenic`, `uncertain significance`, `vus`, `likely benign`, `benign`, and `conflicting`, used alone, `total_found` is the classified match count and windows hold matching records only. With `min_review_stars` or any other significance term it counts search candidates, so a window can retain fewer rows than `limit`, or none, while later windows still hold matches. Report `unavailable_ids` as gaps. The default `limit` is 10; pass a larger one (up to 1,500) to walk a gene in fewer calls.
- Before combining staged windows or genes, account for table replacement: another list call at offset 0 on the same canvas replaces `gene_variants`, and another ClinVar call replaces `clinvar_variants`. A list page past offset 0 never replaces `gene_variants`. Query or retain the current result before advancing, or use separate canvases. Reusing a canvas does not append rows.
- Before reading a catalog count or row as observed variants, check `qc_status` and `qc_filtered`. A `filtered` row failed gnomAD QC in every callset carrying it, often `AC0` (no high-quality carrier) at AF 0, so it passes any `max_af` and sorts first under `ORDER BY af`. Count, rank, or describe only `pass` rows as observed — pass `pass_only`, or filter on `qc_status` in SQL — and report the filtered rows separately. The two differ on `gnomad_r2_1`: filtering staged rows on `qc_status = 'pass'` keeps each row's counts summed over every carried callset, a QC-failed one included, while `pass_only` reads them from the passing callsets only (as gnomAD's browser table does) and applies `max_af` to that frequency. Use `pass_only` when the counts must match the browser's default view. On `gnomad_get_variant`, read `callsets.*.filters` for the reason; a filtered record is a QC-failed call, neither an observed carrier nor proof of absence.
- Before describing a frequency-filtered catalog as rare variants, separate rows with null AF. They survive the maximum-frequency filter because their frequency is unknown. The same holds for null `faf95_max` under `max_faf` (and for a null `faf95` on a variant record): gnomAD reports no filtering allele frequency for AC 0 and singleton variants, on every `gnomad_r3` and `exac` list row, on `exac` variant records, and on `gnomad_r4` and `gnomad_r3` subset variant records, so the row survives the filter untested. Count it as unknown, not as below a disease threshold. Test a disease threshold (ACMG/AMP BA1, BS1) against `faf95` or `faf95_max`, not raw AF.
- Before reading a co-occurrence result, read `variant_ids`: gnomAD can return the pair in the other order than sent, and every count key names `variant_ids[0]` first. The inputs are GRCh37 IDs and the tool always reads `gnomad_r2_1`; convert a GRCh38 ID through `gnomad_get_variant` on `gnomad_r2_1` and use its `candidates` when it fails as `variant_not_found_other_build`; an ID that `gnomad_r2_1` finds is a different variant. When `het_het + het_hom + hom_het + hom_hom` is 0, no sample carries both variants: the probability then comes from each variant's separate data (it is 1 whenever each variant has carriers), reflects that no sample carries both and not an observed phase, and ignores samples not covered at both sites, so read it with the coverage of both positions. A null probability is no estimate, never 0, and the notice's calibration caveat applies, most where both variants are very rare.
- Before reading constraint, check which table answered. A subset reads its parent release's table (`constraint_release` names it), `oe_lof_percentile` exists on gnomAD v4.1.2 only, and the missense and synonymous intervals are null on `exac`. A mitochondrial gene has no nuclear constraint: read `mitochondrial_constraint` (`kind` protein or rna; sums of maximum heteroplasmy, not variant counts), and do not apply the nuclear LOEUF thresholds to it.
- Before reading a subset's coverage as the subset's own, read `coverage_dataset`: gnomAD publishes no subset coverage, so the figures are the parent release's over all of its samples.
- Before treating a `gnomad_list_gene_variants` page as the full candidate set, compare it with `total` and follow `next_offset` until it is null, or aggregate over the staged table. Each page re-fetches the target, so narrow with filters and raise `limit` for a large gene. Without a canvas, exhaustive counts and rankings need every page; a ClinVar window then holds every row of its window, and `next_offset` reaches the rest.

## Core chain

For gene-panel curation: resolve the HGNC symbol → search ClinVar → inspect each retained allele and its review evidence → retrieve its gnomAD population record → apply the single-candidate triage workflow where further interpretation is needed.

Keep clinical classification, population frequency, predicted consequence, and gene constraint as separate evidence axes. Within ClinVar, a somatic classification (`oncogenicity_*`, `clinical_impact_*`) is its own evidence axis: it speaks to tumor biology, not germline pathogenicity, reuses germline words, and carries no star rating, so never read it into `clinical_significance` or the star filter. A ClinVar classification is not a population observation; an absent ClinVar entry is not a benign classification. A failed optional ClinVar annotation leaves population evidence usable while clinical annotation remains unknown.

## Workflows

### Follow ClinVar candidates into gnomAD

Process one ClinVar window at a time. Inspect or query all retained rows, select alleles with usable identifiers, and fetch their population records. Preserve the ClinVar VariationID alongside the resolved gnomAD variant ID so each conclusion can be traced back to the candidate. Resolve unmapped alleles rather than dropping them silently; state any candidates that could not be followed into gnomAD. Finish the window before advancing when reusing its canvas.

### Screen a gene variant catalog

Use `gnomad_list_gene_variants` to select candidates by consequence and frequency, then `gnomad_get_variant` for the selected IDs' full ancestry vectors and annotations. The catalog's joint AF is a screening value; it does not replace the detailed population record. Keep unknown-frequency rows distinct from measured rare rows, and do not turn a catalog shortlist into an unsupported pathogenicity ranking. A row's `consequence` is the most severe term in the gene and can sit on a minor isoform: where `consequence_transcript` is `other`, read the selected variant's `primary_transcript`, which covers the gene in its `gene_symbol`, before calling it pLoF. A null `primary_transcript` means the variant lies outside the gene's MANE Select and canonical transcripts altogether, not that the consequence there is unknown. A row's `lof` (LOFTEE's call: HC high-confidence, LC low-confidence, or OS other splice) follows `transcript_id` the same way, so on an `other` row it is a minor isoform's call; `lof_confidence: HC` narrows the catalog to high-confidence LoF, and a gnomAD LoF curation on `gnomad_get_variant` can overturn a LOFTEE call. Pass `annotations: true` to add HGVS, LOFTEE filter and flags, and rsIDs.

### Phase a pair of rare variants in a recessive gene

With two rare heterozygous variants in one gene and no parental samples, use `gnomad_get_variant_cooccurrence` after each variant's own record: it estimates, from gnomAD v2.1 exomes, whether they sit in trans or in cis. Confirm both variants are coding or UTR variants of the same gene, on GRCh37, and in gnomAD's exomes at allele frequency of 5% or less; any other pair fails as `cooccurrence_unavailable` with gnomAD's reason, and resending it fails again. Report the probability with its counts and the notice's caveat, and treat it as supporting evidence, not a phase call.

### Analyze staged results

With the canvas off, the dataframe tools are not offered and every result is inline. Otherwise, results too large to return inline are staged as a DataCanvas table, and the response carries a `canvas_id`; the list tool stages only at offset 0. Call `gnomad_dataframe_describe` with it for the staged table and column names before writing SQL, then `gnomad_dataframe_query` with a read-only query. The `gene_variants` table's columns follow `annotations` (the default set, or with it the default set plus `hgvsc`, `hgvsp`, `lof_filter`, `lof_flags`, `rsids`); a reused canvas takes the latest call's shape, so call `gnomad_dataframe_describe` again after switching it. Pass the same `canvas_id` back to stage further results beside the first; the tables expire with the canvas. Different table names can coexist; repeated calls producing the same table name replace that table as described above.

For exhaustive analysis, aggregate over the staged table rather than the preview. When retrieving query rows in pages, use a stable ordering with a unique key and follow the returned continuation. `gnomad_dataframe_query` pages default to 25 rows (a `limit` above 3,000 is clamped), and `BIGINT` values such as `ac`, `an`, and `COUNT(*)` arrive as strings; `CAST(col AS INTEGER)` returns a number. If the query reports a cap or unknown total, narrow or aggregate the query before claiming completeness.
